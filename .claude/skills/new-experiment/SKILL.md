# New experiment

Each experiment is its own pnpm workspace under `experiments/<name>/`. The code
is the _means_; the writeup, the raw measurements and the decision trail are the
_output_. An experiment is not done until all of them exist and agree.

## This repo is public

Everything committed here is published. Nothing proprietary goes in: not in
code, prompts, test fixtures, recordings, CSVs, logs, or the blog.

- **No company or customer data.** No internal prompts, product code, customer
  conversations, user IDs, internal URLs, or anything copied from private repos
  or dashboards. When an experiment needs realistic input, generate synthetic
  data (seeded, via a script) or use public datasets, and say so in the blog.
- **No credentials or account identifiers.** Keys live only in the gitignored
  `.env`. `@experiments/test` masks auth headers, org/project/workspace IDs, rate-limit headers and cookies
  before writing recordings, but check any new provider's response headers
  for identifiers and add them to `SENSITIVE_HEADERS` in
  `packages/test/src/record.ts` before committing its recordings.
- **Review before committing.** Grep new recordings and results for
  `organization`, `project`, `workspace`, `ratelimit`, `cookie`, `sk-`, `AIza`, emails and internal
  hostnames. If something private slipped in, delete it and re-record rather
  than editing the HAR.
- **Write for outsiders.** The blog and log shouldn't reference internal
  projects, roadmaps, or why the company cares. Frame the question on its own
  merits.

If the user asks for something that would require private data, say so and
propose a synthetic or public substitute.

## 1. Pin down the question

Before creating files, get a one-sentence question the experiment answers
(e.g. "Does changing `toolConfig.mode` between turns break Gemini's implicit
cache?"). If the user's ask is vague, propose one and confirm. Pick a
`snake_case` name from it (`config_cache`, `gemini_local_tokens`).

If the question is really a follow-up to an existing experiment, check
`experiments/` first. Spin out a new one only when it's a different question;
otherwise add to the existing log.

## 2. Scaffold

```
experiments/<name>/
  package.json
  tsconfig.json
  vitest.config.ts
  src/                 # reusable logic, imported by scripts and tests
    *.test.ts          # tests, co-located with the code they cover
  scripts/             # one script per results CSV, plus build-report.ts
  results/             # *.csv, only ever written by scripts/
  report.html          # generated by scripts/build-report.ts, never hand-edited
  blog.md
  log.md
```

### `package.json`

```json
{
  "name": "@experiments/<name>",
  "version": "0.0.0",
  "private": true,
  "type": "module",
  "scripts": {
    "typecheck": "tsc --noEmit",
    "test": "vitest run",
    "report": "tsx scripts/build-report.ts"
  }
}
```

Add one script entry per run script (e.g. `"bench": "tsx scripts/run-bench.ts"`).

Then add deps with pnpm, never by hand-editing versions:

```sh
pnpm --filter @experiments/<name> add @experiments/shared ai
pnpm --filter @experiments/<name> add -D @experiments/test
```

Shared dev tooling (typescript, tsx, eslint, prettier, vitest, `@types/node`)
lives at the repo root. Don't reinstall it per workspace.

### `tsconfig.json`

```json
{
  "extends": "../../tsconfig.base.json",
  "compilerOptions": { "outDir": "dist" },
  "include": ["src/**/*", "scripts/**/*"]
}
```

### `vitest.config.ts`

```ts
import { defineConfig } from "vitest/config";

export default defineConfig({
  test: { include: ["src/**/*.test.ts"], environment: "node" },
});
```

### `log.md`

```md
# <name> log

Chronological notes: what was tried, what was found.

## YYYY-MM-DD: <the question, as first posed>

<why this experiment exists, and the plan>
```

### `blog.md`

Start with a title phrased as the question and a `## Method` / `## Findings` /
`## Takeaways` skeleton with a sentence or two of intent under each. It gets
filled in as results arrive, not at the end.

Use real dates (today's date from context), never "today" or "yesterday".

## 3. Tests

Tests pin down the behaviour the experiment depends on: helpers in `src/`,
request shapes, parsing of provider responses, and small end-to-end sanity
calls. Import `describe` / `it` / `expect` from `@experiments/test`, not
`vitest`. Every `it` is wrapped in Polly recording, so LLM calls are recorded
once and replayed after.

```sh
RECORD=true pnpm --filter @experiments/<name> test  # wipe and re-record
RECORD=new  pnpm --filter @experiments/<name> test  # replay known, record new
pnpm --filter @experiments/<name> test              # replay only (default)
```

Commit the recordings under `test/__recordings__/`. Don't mark recorded tests
`.concurrent`.

Tests are for correctness of the harness. The measurements themselves come
from `scripts/`, which hit live APIs.

## 4. Scripts and results

- Every CSV in `results/` has exactly one script in `scripts/` that produces it.
  Re-running the script regenerates the CSV from scratch. CSVs are never
  hand-written or hand-edited.
- One row per trial/run. Include enough columns to re-derive every number
  quoted in the blog (model, variant, seed, raw token counts, timestamps),
  not just the summary.
- Put a header comment at the top of each script stating the question, the
  per-trial procedure, and what outcome would confirm or refute the hypothesis.
- Make knobs env-overridable (`MODEL`, `RUNS`, etc.) with sensible defaults.
- Keep reusable logic in `src/` so tests can cover it.

## 5. `report.html`

The HTML output is the visual companion to the blog. `scripts/build-report.ts`
reads `blog.md` and `results/*.csv` and writes a single self-contained
`report.html`: the post rendered to HTML, with tables and charts built from the
CSVs in place of (or alongside) the markdown tables.

- Generated, never hand-edited, so it can't drift from the data. Re-run
  `pnpm --filter @experiments/<name> report` after any results or blog change.
- Self-contained: inline CSS and data. Libraries only from a CDN
  (cdn.jsdelivr.net / cdnjs), no local asset files.
- Works in light and dark mode and at phone width.
- Load the `dataviz` skill before writing chart code.

## 6. While running the experiment

- **Append to `log.md` immediately** after each attempt: what was tried, what
  happened (with numbers), what was learned. Dead ends, surprises and bugs in
  the harness count. Don't batch it up for the end.
- Update `blog.md` as findings firm up. It draws from the log and the CSVs,
  cites the script and CSV behind each claim, and is written for someone who
  never saw the log.
- Rebuild `report.html` whenever results change.

## 7. Done means

- [ ] `blog.md` answers the question, with Method, Findings and Takeaways, and
      cites `scripts/*` and `results/*` for every result.
- [ ] `log.md` has dated entries covering every run, including failures.
- [ ] Every `results/*.csv` is reproducible from its script.
- [ ] `report.html` rebuilt from current data.
- [ ] `pnpm --filter @experiments/<name> test` and `typecheck` pass, and
      `pnpm lint` is clean.

Report back to the user with the headline finding and the path to
`report.html`.
